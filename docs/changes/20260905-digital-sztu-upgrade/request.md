是的，Obsidian 的图谱主要由本地 Markdown 笔记及其链接支撑；HTML 可以作为我们图谱的浏览界面。 你对 README 的顾虑也成立：GitHub README 能展示图谱预览，但不能直接运行我们自己的交互图谱代码。
Obsidian 大致有三层：
1. 笔记文件：一个 Vault 本质上是本地文件夹，里面保存 .md 笔记和附件。
2. 链接与索引：笔记中的内部链接形成关系，Obsidian 维护本地元数据缓存，记录文件和链接信息。
3. 图谱界面：应用读取这些信息，把笔记画成节点，把内部链接画成边，提供缩放、点击和局部关联探索。图谱不需要作为一张图片手工维护。Obsidian 数据存储说明、图谱说明
例如，某个项目.md 中写了 [[某个组织]]，就能形成一条笔记链接。但这条连线本身只说明“笔记引用了另一篇笔记”，具体是组织开发了项目、资助了项目，还是文章只是提到了组织，需要内容进一步解释。我们有来源和事实核查要求，因此保留 JSON 中明确的关系类型、论断和证据，会更适合。

把同一套静态 HTML／CSS／JavaScript 发布到 GitHub Pages，再从预览图链接过去。这只需要静态托管，不必同时建设复杂的线上系统；但它属于另行发布的网页，仍然不会在 README 内直接运行。[GitHub Pages 说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## 1. 技术方向与项目定位

**采用本地 JSON／Markdown 保存档案，由同一套构建流程生成交互 HTML、README 静态预览和 Markdown 档案目录；精简交互图谱同时发布到 GitHub Pages。**

Obsidian 的图谱由本地 Markdown 文件、内部链接及应用维护的索引支撑；Markdown 本身不会绘制交互图谱。它同时支持标准 Markdown 链接与 wikilink，因此我们的可阅读档案目录也可以采用通用 Markdown 链接，兼顾 GitHub 和 Obsidian。[Obsidian 数据存储](https://obsidian.md/help/Files%2Band%2Bfolders/How%2BObsidian%2Bstores%2Bdata)、[内部链接](https://obsidian.md/help/links)

## 3. 同一份档案，生成三种呈现

| 输出 | 用途 | 本次行为 |
|---|---|---|
| **交互 HTML** | 沿档案关系探索 | 本地打开和 GitHub Pages 共用同一个精简查看器 |
| **SVG 静态预览** | 在 README 内直观展示 | 由真实档案关系自动生成，点击进入在线交互图谱 |
| **Markdown 档案目录** | 在 GitHub 直接阅读和互相跳转 | 自动生成总目录、分类目录及逐条档案页面，附来源和反向链接 |

**交互图谱**

- 默认以画布为主，不设置常驻左右侧栏。
- 提供搜索定位、拖动、缩放、重置，以及全部档案／聚焦所选切换。
- 点击节点显示可收起的详情，查看摘要、正文、相关档案和来源；局部图默认展开一层关联，可继续展开。
- 类型筛选按需打开；事实关系与分类、集合、wikilink 等导航关系明确区分。
- 来源默认在详情中查看，需要时展开为节点。图谱连线全部来自正式记录，不根据名称相似、空间距离或研究社交关系生成。
- 本地版本通过 `digital-sztu graph --open` 打开，静态资源随工具分发，普通使用者无需安装 Node.js。
- 本地与线上使用同一份允许公开展示的档案数据；仅运行位置不同，不维护两套内容或界面。

**README 与 Markdown**

- README 嵌入固定路径的 SVG 预览；数据更新时重新生成 SVG，不自动改写整篇 README。
- 静态图保留真实节点和关系；较大图谱可以减少文字标签，但需说明展示范围，不伪造关系或统计。
- GitHub 会清理 README 中的自定义脚本，因此搜索、拖动和展开在链接过去的独立页面运行。[GitHub 渲染流程](https://github.com/github/markup)
- Markdown 页面使用稳定 ID 对应文件名、标准相对链接和来源定位；生成页面注明真源位置，修改应回到正式记录。
- 这些 Markdown 页面是阅读视图，不成为第二份需要手工维护的事实真源。

## 4. 构建更新与 GitHub Pages

- `digital-sztu build` 从正式记录生成公共图谱数据、SVG、Markdown 目录和查看器所需内容；`digital-sztu graph --open` 确保输出已更新后打开本地页面。
- 所有输出使用同一份公开数据筛选结果与内容版本标识。排除项不得通过反向链接、节点详情、静态预览或 Markdown 页面重新出现。
- SVG 和 Markdown 目录作为派生产物随相关档案变更提交；CI 重新构建并检查差异，防止 README 预览与正式档案脱节。
- 本地 HTML 放入 `.work/graph/`；Pages 构建产物进入独立暂存目录，发布时仅上传明确的静态站点产物，不上传整个仓库、研究台账或缓存。
- 仓库更名后启用 GitHub Pages 的 Actions 发布方式；默认使用项目 Pages 地址，不配置自定义域名。
- PR 执行校验与构建；`main` 更新且所需检查通过后部署。发布任务依赖验证任务，只授予发布所需权限，并使用 `github-pages` 环境。[GitHub Pages 自定义工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
- README 预览链接到在线精简图谱，并保留直接阅读 Markdown 目录和本地使用的入口。

**三栏线上布局仍只记录需求。** 保存本次概念图与“左侧筛选、中间图谱、右侧详情”的说明，作为未来界面参考；本次 Pages 发布沿用精简查看器，不增加账号系统、后台编辑或 RAG 问答。

**执行顺序：** 独立工作区 → 更名兼容、模型与研究工具 → 精简图谱及三种输出 → 隔离样例验证 → 完成普查 → 正式入库 → 真实内容验证 → 推送并合并 → Pages 发布及线上核验。

- **三种呈现一致：** HTML、SVG、Markdown 与图谱数据对应同一内容版本；无悬空链接、伪造关系或候选数据误入。
- **浏览体验：** 验证本地离线打开、线上打开、搜索、缩放、节点展开、详情阅读及来源跳转；检查中文、特殊字符、小屏布局、空数据和较大数据集。

最终交付必须包含已经核验并入库的真实内容，README 能看到预览，点击可以探索，同时保留本地使用和直接阅读 Markdown 的能力。
